# 风险、诊断与批量运营中心

本模块把安全事件、外部服务可用性、Telegram 告警、账号生命周期和交易对账纳入共享业务层。Bot、Web API 与后台 Worker 使用同一数据库和任务队列，避免同一操作在不同入口产生不同结果。

## 风险规则与诊断

管理后台的“诊断中心”提供以下能力：

- 主动探测数据库、Emby、Telegram API，以及已启用的 MoviePilot。
- 保存每次状态、响应码和耗时，并在服务首次异常、恢复时产生系统事件。
- 按事件类型、时间窗口和次数阈值执行风险规则，支持 `auth.*` 形式的通配匹配。
- 为每条规则配置风险级别、冷却时间、是否启用及是否发送 Telegram 告警。
- 记录告警接收人、尝试次数、失败原因和最终送达时间。

Bot 默认每 60 秒执行一次探测。可以在 `.env` 中调整：

```env
SAKURA_DIAGNOSTIC_INTERVAL_SECONDS=60
SAKURA_PROBE_RETENTION_DAYS=30
# 可选；留空时使用 config.json 的 owner 和 admins
SAKURA_ALERT_TELEGRAM_IDS=1029558707,123456789
```

修改环境变量后需要重新创建 Bot 容器。诊断任务由 Bot 容器执行，因为 Telegram 告警需要已经启动的 Telegram Client。

## 通知联动

充值、退款、工单、求片、影评和账号生命周期通知都会读取用户的通知偏好：

- 开启站内通知时写入 Web 通知中心。
- 开启 Telegram 通知时创建后台发送任务，失败会自动重试三次。
- 两个渠道可以独立关闭；关闭站内通知不会再意外阻断 Telegram 通知。

安全管理员告警使用独立送达记录，不与普通用户通知混合。

## 账号生命周期与批量运营

“批量运营”页面支持一次提交最多 500 个 Telegram ID，并要求管理员二次确认。可执行：

- 暂停、恢复或清理 Emby 账号；
- 延长账号有效期；
- 增减积分或注册资格天数；
- 批量发送站内与 Telegram 通知。

每个用户独立执行，单个失败不会终止整批任务。任务队列保存整批状态，账号生命周期表保存逐用户结果，审计日志保存操作者与变更详情。清理账号只删除 Emby 账号和本地绑定信息，不删除 Telegram 用户档案。

## 退款与交易对账

已入账充值订单可以由具备 `billing:update` 权限的管理员退款。退款会原子执行：

1. 检查订单处于已入账状态；
2. 检查用户当前积分足以冲正；
3. 扣回本订单的基础积分和赠送积分；
4. 写入负向积分流水、退款账单、审计事件和用户通知；
5. 将订单标记为已退款，重复请求不会再次扣款。

批量运营页面同时显示充值订单对账摘要，包括超过 24 小时的待处理订单、已入账但缺少账单流水的订单，以及重复入账流水。

## 上线检查

拉取新镜像并重新创建服务后，`migrate` 容器会自动升级到迁移 `20260731_09`。随后检查：

1. `migrate` 正常以退出码 0 结束；
2. Bot 日志出现 `monitor_diagnostics` 定时任务；
3. 管理后台“诊断中心”可以产生数据库、Emby 和 Telegram 探测记录；
4. 测试告警可以进入任务队列并显示送达状态；
5. 批量操作先用一个测试用户验证，再扩大目标范围。
